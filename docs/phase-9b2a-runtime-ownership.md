# Phase 9B.2a：持久单实例占用与核心离线操作

本阶段保护 Gateway 运行实例、显式迁移，以及 backup / restore / verify-restore 命令。独立反馈采集和其他维护 CLI 的完整注册与互斥仍留在 9B.2b；9B.2 整体尚未完成，不因本阶段而宣称生产就绪。

## 为什么不使用自动过期租约

数据库会话断开不代表原进程已停止，更不代表远端未接受 DATA。仅依赖 advisory lock 或 heartbeat 超时后自动接管，会让新实例和仍在发送的旧实例重叠。

新增 public.runtime_owner 单行控制表，由主键强制最多一份占用，mode 区分 runtime / offline。记录 owner UUID、主机/进程 ID、专用 PostgreSQL backend PID、开始与最近联系时间，不存邮件或凭证。控制表固定在 public，不能通过改变 search_path 绕过同数据库的占用。

占用同步提交后才允许启动监听、同步身份和运行 worker。专用连接持有会话锁并每秒联系一次，单次检查两秒超时。last_seen_at 仅用于排查，不是自动释放时间；记录没有 TTL。

正常退出等待 HTTP、SMTP、maintenance、worker 和 Webhook 收尾完成后清除自己的准确 owner UUID。启动尚未启动后台任务就失败时可正常释放。连接丢失、退出超时、监听异常或其他运行错误保留记录；ready 不再报告正常，并停止领取/监听、进行有界收尾。不能保证撤回已经交给远端的 DATA，UNKNOWN 仍保守保留。

## 离线命令

迁移、backup、restore、verify-restore 在持有迁移准入锁期间检查占用。已存在运行或遗留占用时拒绝操作；离线操作进行中，启动登记被阻止。已有控制表的数据库会登记 offline 占用；失去专用连接时取消命令并保留记录。所有这些命令仍要求操作者真正停止所有发送和写入进程。

首次迁移或空目标恢复尚无控制表时使用数据库准入锁与断连取消；空库无法通过 schema 启动检查，恢复过程还有 9A 文件启动闸门。不能将这一引导路径当作旧版本进程互斥保障。

备份排除 runtime_owner 数据，并且不对控制表施加全程 SHARE 表锁，避免把正常 heartbeat 阻塞成断连。控制表 schema 仍随备份恢复，恢复后没有旧进程占用；恢复启动闸门与外部发送对账要求保持不变。内部恢复函数增加占用校验，但完整互斥由受支持的 CLI 入口持锁保证，嵌入调用不能跳过入口协议。

## 异常停机后的人工处理

先执行 `relaytale list-runtime-owner`，查看准确 owner_id、mode、主机及进程信息。不要因为最近联系时间陈旧、数据库 backend 消失或主机 PID 不存在就直接认为邮件未发送。

1. 确认原主机上的原进程与全部发送/文件写入操作确实停止；必要时先停止容器或相关服务。
2. 核对不确定投递与恢复闸门。切断数据库连接不是停止原进程的替代办法。
3. 使用准确 owner_id 执行：

```sh
relaytale release-runtime-owner --owner-id '<观察到的 UUID>' \
  --confirm-stopped --actor '<操作者>' --reason '<已停止与对账的证据>'
```

该命令拒绝缺少确认、错误 UUID、仍持有专用会话锁的进程以及正在执行的离线操作。清除与 maintenance_audit 记录同事务提交，审计含原 owner UUID 和操作理由。数据库只能核对会话锁及准确占用，跨主机进程真正停止仍需要操作者证据。不会自动重试 UNKNOWN、删除邮件或绕过 restore marker。

不要用 DELETE 控制表、时间阈值、周期任务或频繁重启实现自动接管。Compose 的异常重启可能持续被遗留占用阻止，这是有意的保守选择。单实例约束按数据库生效；为另一个数据库配置同一 EML 目录仍不受保护，禁止共享目录。数据库超级用户、手写 SQL、旧版本及未登记工具可以绕过协议，不属于防护边界。
