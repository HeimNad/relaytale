# Phase 8E.2c · 消息流预算与公平调度

2026-10-04。新增网站消息流准入预算、身份轮转和流内加权轮转。沿用保守投递语义：调度只选择可领取任务，不放宽重试/failover 条件，不自动重发 UNKNOWN，也不保证送达时限。邮件有效期仍留在 8E.2d。

## 消息流配置与提交

`SEND_API_KEYS` 每个身份可增加 `streams`。名称固定为 `normal`（普通通知）、`otp`（验证码）、`security`（安全提醒）、`receipt`（订单收据）；这些名称没有自动检测邮件内容或不同 IP 线路的含义。

```json
[{"id":"<稳定 UUID>","token":"rts_<32 字节随机值的小写十六进制>","allowed_from":["sender@example.test"],"budget":{"day":2000},"streams":[{"name":"normal","weight":1,"budget":{"hour":200}},{"name":"otp","weight":3,"budget":{"minute":20,"day":1000}}]}]
```

这是占位示例。每个流的权重必须显式指定为 1..8，同名不可重复。未列出的非普通流不接受新请求；`normal` 始终存在，省略时自动补权重 1、流预算不限。整项 streams 省略则保留旧入口行为，只允许 normal。流预算采用已有 minute/hour/day 三个滚动窗口，0/省略表示该窗口不限，单位是**新接收的信封收件人数**。

HTTP 网站请求通过单个 `X-RelayTale-Stream: otp` 选择已授权流；省略等同于 normal。空值、重复头和未知名称返回 400；未授权流返回 403。客户端不能提交调度权重或抢占式最高优先级，修改权重只能通过管理员环境配置和重启。

新请求必须同时满足网站总预算与对应流预算。流额度不足返回 429 `stream_budget_exhausted`，`Retry-After: 60` 只是重查建议。单次收件人数超过任一预算总上限仍返回 422 `recipient_batch_exceeds_budget`。超额或未授权请求不会发布正式 EML，也不会留下幂等占位。

配置持久化并审计，新的准入在网站身份锁下检查当前数据库流策略，旧进程不能靠缓存策略接受已撤销流的新邮件。删除非普通流配置会禁止该流的新提交，但不取消已经接受的邮件：历史策略保留用于处理积压，不清空额度。重新加入时历史窗口用量继续生效。各进程须使用一致管理员配置，仍不宣称支持多实例配置协调。

## 幂等与可见性

- 流名不可在接受后修改。同键同原文改流属于不同请求，返回 409；同键同流重放不再次扣额或投递。
- 省略流和显式 normal 保留既有 v1/v2 请求指纹，老请求在升级后仍可重放。非普通流使用内部 v3 请求指纹；它不是状态 API 的 schema version。
- 流被撤销后，当前 HTTP 身份不再授权该流请求，包括通过该入口的重放；已有消息仍可按原 message_id 查询，不需要换键重新发信。
- 原始 MIME、Message-ID 和业务标签不会被改写。SMTP 原文中自带的类似头也不被当成调度授权。
- 单封状态查询在成功响应的 `X-RelayTale-Stream` 头返回流名；原有 JSON v1/v2 和已冻结的 Webhook payload 不变。列表 JSON 暂不增加流字段/过滤。管理消息详情及 MESSAGE_RECEIVED/ATTEMPT_STARTED 审计包含流名。
- 网站和流预算都按新提交计费；Provider 线路/账号组预算仍按投递尝试计费。失败、抑制或 UNKNOWN 不退款，只有未提交事务回滚撤销预留。

## 双层调度

第一层以稳定 API 身份或 SMTP 账号为单位，选择最久未获得领取机会的可用身份。一次领取完成后，把该身份排到后面；空闲身份恢复后只获得下一次机会，不累积无限补偿额度。SMTP 当前只使用 normal，不支持从 MIME 指定消息流；没有身份的旧内部记录按来源合并为 legacy 身份。管理员给同一网站创建多个身份会改变其公平份额，不应通过换身份轮换密钥。

第二层在该身份内部进行加权轮转。假设 normal 权重 1、otp 权重 3，且两条流持续可领取，顺序为 normal、otp、otp、otp，再循环。未就绪、受 Provider 额度/路由限制或没有任务的流跳过，不空占机会。四条流权重均至少为 1、至多 8；在策略稳定且流持续可领取的前提下，普通流不会被无限优先级积压压住。它是**领取机会**的公平，不是 CPU 时间、字节数或送达延迟的公平。

每次领取最多 **16 个收件人**，再取单线路和共享组剩余额度的更小值。大批次剩余收件人留在队列，下一次机会继续，已经接受的收件人不重复投递。旧 messages.priority 不再作为全局抢占排序；同一流内按 created_at/id 处理。此次升级会改变多账号积压顺序，并让超过 16 个收件人的消息产生更多 SMTP attempts，应计入上游连接成本。

轮转位置和最近一次领取顺序保存在数据库，和 attempt/预留在同一事务提交；失败回滚不消耗该身份的已提交轮次。全局序列只分配顺序，回滚留下序列空洞没有发送语义。锁顺序为 suppression 共享门闩 → 调度身份 → message → provider → quota group；身份锁用 SKIP LOCKED，不会把全队列串行到一个全局行锁上。网络发送发生在领取事务提交之后，不持有调度身份锁。

公平性以持续有可用路线/额度、事务可完成为前提。账号可能因行锁、停机、预算耗尽、熔断或收件人状态而暂时无法领取；不承诺最大等待秒数。此阶段未进行大规模多账号容量认证，仍需遵守 9B 生产门槛。

## 升级与恢复

迁移把旧消息归为 normal，初始化已有 API 身份的普通流策略，并为历史消息建立调度身份。新消息在数据库触发器中补齐身份行。升级需停止旧 worker，避免旧代码绕过新的预算和调度规则；回滚迁移要求显式方案。

备份保留消息流、流预算/权重、调度轮转位置和顺序序列。恢复验收检查消息存在对应调度身份、预留与消息流一致。旧版备份应使用与其版本兼容的恢复流程后再升级，不保证跨版本直接恢复。

## 验证

旧幂等、业务关联、网站预算、共享 Provider 预算回归已通过。新增验证覆盖流授权/撤销、数据库二次检查、流预算耗尽、流变更幂等冲突、普通流指纹兼容、MIME 保持、两个网站交替领取、1:3 加权机会、重新创建 worker 后轮转延续、20 收件人按 16+4 投递、领取回滚不推进调度，以及恢复流策略/轮转状态。

首轮全量回归发现旧 Webhook 测试依赖全局 FIFO：同时入队三个身份，却只领取一次并断言首封产生结果通知。公平调度不再保证该顺序。测试改为处理三个身份，并同时断言订阅消息只有一次 SMTP attempt、未订阅身份没有 Webhook；没有放宽通知隔离断言。

完整 `make ci` 已通过：格式检查、`go vet ./...`、`go build ./...`、`go test -race -count=1 -timeout=8m ./...`，其中隔离 PostgreSQL 全量集成测试耗时约 149 秒。全部邮件测试使用 Fake SMTP，未向真实收件人发送。
