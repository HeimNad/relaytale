# 业务网站能力规划：小型 SMTP Provider 之上的 RelayTale

调研日期：2026-09-27。本文保留需求依据与排期；截至 2026-10-01，8D 查询/回调与 [8E.1 业务关联](phase-8e1-business-reference.md) 已完成本地验收，其余条目按路线图推进。

## 判断依据与定位

本轮核对 Postmark、Resend、Brevo 的官方产品/API 文档，以及 SpaceMail、Purelymail 的限制说明。成熟产品反复出现的能力可以说明它们是常见业务场景，但不是需求量调查；没有使用付费转化、工单数量或用户调查数据。因此下文“高优先级”是结合业务损失、现有缺口、适配成本的产品判断，不是市场排名。

RelayTale 的目标是给已有邮箱 Provider 补上业务系统需要的控制、关联、隔离和反馈能力。网关能管理自己的队列，不能凭空获得 Provider 未提供的最终送达/投诉事件、实际余额或更好的出口 IP 信誉，也不能通过切换账号绕过服务商限制。未查到公开接口不等于证明接口不存在。

当前已有持久化原文、逐收件人状态、保守重试/切换、Provider 配额与健康、全局 suppression、独立发信身份、管理 UI、审计及停写备份。下面是在这些能力上补缺口，不重新实现第二套队列。

## 优先级与业务场景

| P1，8E.1 | 业务关联与检索 | 客服拿订单号无法找到对应邮件 | 已实现有界 client_reference/标签、身份范围检索、审计和显式 v2 回调 |
| P1，8E.2 | 网站与邮件类型隔离、预算 | 一个网站失控耗尽全部额度，验证码排在普通通知后 | 在现有 API 身份和 Provider 配额之上增加项目预算、消息流、合理公平性 |
| P1，8E.2 | 验证码/重置邮件有效期 | 故障恢复后发送已经失效的验证码 | 新增 expires_at、领取与 DATA 授权前过期检查；不撤回已经发出的邮件 |

| P1，9B 并列 | Provider 能力档案、域诊断与告警 | 密码失效/额度耗尽/域配置改变后才发现收不到信 | 补来源可追溯的限制配置、诊断和聚合告警，不宣称知道远端实时余额 |

| P2，8G | 定时、取消与替换待发通知 | 预约取消了，旧提醒仍会发；重复点击发多封提醒 | 显式时间与取消边界，不能把“取消请求已收到”当作“邮件已撤回” |
| P2，7C | 网站范围的偏好/抑制查询 | 网站继续给明确无效或退订的地址发信 | 复用全局保护，新增业务范围与原因；不把所有 5xx 当地址无效 |

| P3，10A | 用户回复进入网站 | 用户回复通知邮件后，希望进入工单/订单讨论 | 独立入站处理与回调；普通回复不是 DSN，不直接信任 From |

P0/P1 表示本项目的实施优先级，不表示每项都属于安全漏洞。9B 的单实例/迁移互斥、最小权限和密钥轮换仍是生产门槛，不能为了 8F 模板等便利功能一直延后。

## 8E.1：把邮件关联到业务，而不是把业务数据写进正文

支持网站自己的不透明关联 ID（例如订单通知任务 ID），与 Gateway message_id 同时出现在查询和通知中。标签可表达 `password_reset`、`order_receipt` 等业务类型，按项目范围检索；关联 ID 不替代幂等键，不作授权凭据。

身份来自已认证的 API key，不能相信请求中的任意 project_id。metadata 约束键数、总字节与可查询字段，不允许借它记录验证码、重置 token 或完整用户档案；不进入 Prometheus 高基数标签。默认只存数据库，不插入原始 MIME。所有会改变发送/策略语义的字段纳入版本化请求指纹，同一幂等键但不同参数必须冲突。

与 8D 的衔接：第一版 8D 不依赖完整标签功能，先依靠 message_id；新增字段通过明确 schema_version 演进，不静默改变已有事件结构。

参考：Resend 提供邮件标签；Postmark 文档说明 metadata 可返回到 API 和 Webhook，用于业务关联。[Resend Tags](https://resend.com/docs/dashboard/emails/tags)、[Postmark Manual](https://postmarkapp.com/manual)。

## 8E.2：多网站、公平队列和时效

实现拆分：8E.2a [网站提交预算](phase-8e2a-website-budgets.md) 已接入滚动分钟/小时/24 小时收件人数限制；8E.2b [共享 Provider 额度](phase-8e2b-provider-budgets.md) 已实现显式分组及共同预留校验；8E.2c [消息流预算及公平调度](phase-8e2c-message-streams.md) 已完成按身份及流轮转的本地验收；8E.2d [有效期](phase-8e2d-message-expiry.md) 已完成本地验收。以下保留完整目标，不表示已全部完成。

每个网站独立身份、发件白名单、配额及可访问数据。第一版用于同一操作者管理自己的多个网站，不宣称具备面向互不信任客户的 SaaS 多租户隔离。消息流区分验证码、安全提醒、订单收据和普通通知；客户端不能任意声明最高优先级，允许等级由管理员配置。保留普通流的最低处理机会，防止无限饥饿。

同一个 Provider 账号被配置为 465 和 587 两条路径时，不能当作两份独立发送额度。支持共享账号预算组，保留原有收件人尝试计费和崩溃不退款规则；增加邮件数、收件人数、速率突发及周期窗口的明确单位。网站额度与共享 Provider 额度同时生效，不能通过 failover 把一次应用失控扩散到所有 Provider。

新增 expires_at：过期前才允许提交新的 DATA 授权；每次领取和 DATA 授权都重新检查，并与取消/抑制/授权串行化。已授权 DATA 或结果 UNKNOWN 后不能直接改成“从未发送的过期邮件”，保留实际尝试和不确定状态；过期只能阻止未来尝试。网关不承诺在期限内送达，验证码是否有效仍由网站验证。

业务上的“最新验证码替换旧验证码”另设受身份约束的替换键，只作用于尚未授权 DATA 的任务，不能误取消已经发送或 UNKNOWN 的任务。

参考：Postmark 把事务与广播邮件分成 Message Streams；RelayTale 可借鉴逻辑隔离，但仅划分队列不会自动拥有它们的独立 IP 基础设施。[Postmark Message Streams](https://postmarkapp.com/message-streams)。有效期和公平调度是本项目基于验证码场景提出的设计，不声称这些 Provider 都提供了相同实现。

## Provider 能力与故障可见性

建立每个“Provider 账号 × 发件域”的能力档案，区分人工配置、公开文档和实际协商/受控验证结果，记录来源与最后核验时间。字段包括 TLS/AUTH、SIZE/单次收件人限制、计费单位、共享账号限制、是否支持可验证反馈、是否允许自定义 Return-Path/信封关联标识，以及 DKIM 的责任方。未知就显示未知。

SpaceMail 当前公开页写明试用与付费邮箱存在小时限额，并列出单封收件人和大小限制；Purelymail FAQ 则给出账号外发日量和突发限制。数字可能变更、账号可能有特批，因此不硬编码为默认额度；现有滚动 1h/24h 收件人尝试账本不能直接表示这两种服务商余额。[SpaceMail 官方限制](https://www.spaceship.com/knowledgebase/spacemail-email-limits/)、[Purelymail FAQ](https://purelymail.com/docs/faq)。

域诊断展示 SPF/DKIM/DMARC 配置及对齐线索、证据时间和限制；DNS 配置存在不等于真实签名通过，更不等于入箱。切换 Provider 前复用已验收身份边界。只读诊断不自动改 DNS、不擅自签名/改写 EML。[Resend 域验证诊断](https://resend.com/changelog/domain-verification-events) 是交互参考，不是现有 Provider 验收证据。

告警优先覆盖最老队列年龄、验证码即将过期、认证配置错误、共享额度紧张、UNKNOWN 增长、Webhook 死信、IMAP 游标停滞和磁盘/备份异常。区分 Provider 健康与某一收件域拒绝；稀疏样本不输出误导百分比。告警聚合、去重、有恢复通知，避免故障时逐邮件轰炸；不能仅通过已经故障的邮件通道告警，外部发送目的地由操作者配置。

## 8E.3：真正不会发出去的沙箱

[8E.3a 安全基础](phase-8e3a-sandbox.md) 已实现不可变测试身份、测试存档、零 SMTP 尝试及明确标记的通知。[8E.3b](phase-8e3b-sandbox-tools.md) 已完成下述 MIME 检查、受控结果模拟、网站参考后端与契约；8E.3 整体已完成本地验收。

测试与生产凭证明确分开。测试邮件可以查看 MIME、附件结构、时间线和模拟 Webhook，但 worker 在最终出站闸门强制拒绝真实投递，不依赖 UI 上的 test 勾选。记录 simulation=true，模拟事件使用独立命名/环境；不在生产数据里伪造 SMTP_ACCEPTED/DELIVERED。测试模式转生产不能放行历史测试队列。

先提供一套小型网站示例与 HTTP/OpenAPI 契约：提交、持久化 message_id、相同幂等键重试、状态查询、验签、通知去重和乱序处理。按真实接入需求补 PHP/Laravel、Node.js、Python；不一开始维护所有语言 SDK。SMTP 应用另有最小改动接入指南，不让它们被迫迁移 API。

Postmark 有不实际送达的沙箱模式；RelayTale 采用明确模拟标记，避免把测试展示和真实送达事实混淆。[Postmark Sandbox](https://postmarkapp.com/developer/user-guide/sandbox-mode)。

## 8F / 8G：便利能力保持可复现

JSON 发信允许 text/html、附件及 Reply-To 等有界字段，服务端生成 MIME；现有 raw EML 透明入口不变。先做最小 JSON 构建，再做固定版本模板、变量校验、预览、语言版本与显式发布。渲染器不访问网络或执行代码；生成后的 EML、模板版本和规范化参数指纹固化，重试不能因模板后来修改而改变正文。附件不得直接抓取任意 URL。

定时发送使用明确带时区时间并落为 UTC；约束 schedule_at、expires_at、最大排期及排队容量。取消与 DATA 授权争抢同一状态边界：已经授权/可能发出就明确返回不能保证撤回。批量发送必须逐消息报告接受/失败，逐消息幂等，不能把一批成功解释成所有收件人成功。

这些是成熟产品已有的便利能力，但不优先于结果可见和投递安全。[Postmark Templates](https://postmarkapp.com/developer/api/templates-api)、[Resend 定时/改期/取消](https://resend.com/docs/dashboard/emails/schedule-email)。

## 偏好、抑制与回复

全局强制 suppression 仍优先。网站可查询自己相关的阻断原因，未来区分“地址已验证无效”“投诉”“某类通知退订”和“人工停用”；偏好不能覆盖全局保护，营销退订也不能被误套到所有安全提醒。网站用户身份与订阅同意由业务系统负责；反馈可见性和自动抑制权限独立。只有可信且能唯一关联的反馈才可触发自动状态改变。[Postmark Suppressions](https://postmarkapp.com/developer/api/suppressions-api) 提供按流管理的产品参考，当前 RelayTale 的全局范围不能静默迁移成按流。

回复转工单属于后续独立功能：Reply-To 路由、不可猜测关联 token、In-Reply-To/References 辅助、附件限额及安全处理、自动回复循环防护、入站重复去重。相关性不等于用户身份认证，不能凭收到一封回信执行退款/改账号等业务动作。原 DSN 收集器不自动变成任意入站邮箱处理器。[Postmark Inbound Webhook](https://postmarkapp.com/developer/webhooks/inbound-webhook)。

## 明确后置或不承诺

- 打开率/点击率追踪：后置、显式选择；不在透明模式中注入像素或改链接，也不把这些信号当业务完成或送达证明。
- 大规模营销群发、联系人 CRM、拖拽编辑器、AI 写信：没有当前业务证据，不进入近期范围。
- “必达收件箱”、自动更换出口信誉、自动读出 Provider 剩余额度：没有相应 Provider 能力和证据就不承诺。
- 任意 5xx 自动加入黑名单、UNKNOWN 自动重发、回调重试触发邮件重发：不实现。

## 实施顺序与验收门槛

1. 8D 查询与回调；7B 的可信来源验证按证据推进，未确认反馈保持隔离。
2. 8E.1 业务关联；8E.2 项目/流预算与有效期；8E.3 沙箱与一个参考网站。
3. 9B 生产门槛与 Provider 档案/告警作为同一优先层推进，不能等全部便利功能做完。最小权限、迁移/单实例互斥和密钥轮换仍需独立验收。
4. 8F 简单 JSON/版本化模板、8G 定时/取消；7C 偏好范围需先明确产品规则。
5. 9C 生命周期与运营视图持续补齐；10A 入站回复有明确业务使用者后再开始。

新增能力均需验证越权、并发边界、幂等重放、UNKNOWN 不自动重发、故障恢复及审计。特别覆盖：两个网站争抢一个 Provider 配额、同账号双端口共享预算、过期/取消与 DATA 并发、模板版本变化后的重试、测试身份无法外发、回调/查询字段不泄漏验证码。
