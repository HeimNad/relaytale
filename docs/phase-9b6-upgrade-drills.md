# Phase 9B.6：升级中断与显式恢复演练

本阶段使用独立临时数据库，将真实 v22 schema 升级到当前版本。在 v23 的版本记录写入处注入故障：此时真实 CREATE TABLE 已经执行，但事务尚未提交。没有增加生产故障开关，也没有连接真实 Provider。

## 演练矩阵

| 故障 | 必须观察到的结果 | 恢复条件 |
| --- | --- | --- |
| 版本记录写入报错 | v23 的 auxiliary_owner 表与版本记录一起回滚；schema 门槛拒绝运行；正常失败清除离线占用 | 排除错误后显式重新迁移 |
| 迁移在版本写入处等待时取消 | 已执行 DDL 回滚；迁移退出；正常取消清除占用；schema 门槛继续拒绝运行 | 确认命令退出，再显式重新迁移 |
| 等待期间离线占用连接被终止 | 监控取消迁移；DDL 回滚；持久占用保留；新迁移与运行占用均拒绝接管 | 确认全部操作停止，按准确 UUID 人工释放，再显式重新迁移 |

测试通过数据库锁等待建立确定性屏障，不依赖固定睡眠碰撞。恢复后重新检查完整迁移历史。测试固定保留 v22→v23 的历史边界，后续增加迁移不会偷偷改变这条回归用例。

## 升级操作顺序

1. 记录当前程序版本、配置与密钥版本；确认备份可验证并保存读取旧凭证所需的密钥。使用 [停写备份流程](phase-9a-backup-recovery.md) 生成配套数据库与 EML 快照。
2. 停止运行服务及独立采集、维护任务。`--offline` 是停写声明，不会代替停止进程。检查运行及辅助占用，不按时间自动释放。
3. 使用专用迁移账号运行新版本 `relaytale migrate --offline`。迁移期间保持运行服务停止；失败时保留错误与版本信息，不执行 Down，不手工伪造版本记录。
4. 迁移成功后，按 [权限部署流程](phase-9b3-database-privileges.md) 重新应用运行账号授权，核对配置、密钥与原文存储。启动一个运行实例，检查 readiness、队列与 UNKNOWN 告警。

## 中断后的人工处置

先停止并确认原迁移进程及其数据库操作已经退出。数据库连接消失本身不能证明原进程已经停止。检查迁移历史与实际对象：`goose_db_version` 是历史记录；启动门槛检查历史一致性，不是完整物理 schema 校验。

正常报错或取消可能已经清除了离线占用；若占用仍在，先查看 `list-runtime-owner` 与 `list-auxiliary-owners`。只在确认原进程、迁移及其他写入已经停止之后，按 [准确 UUID 释放流程](phase-9b2a-runtime-ownership.md) 使用 `release-runtime-owner --confirm-stopped --actor ... --reason ...`，保留核对证据。不能直接删除控制表记录。

排除故障并确认当前状态后，显式再次运行迁移。若无法确认 schema 与历史一致，应保持停写，在隔离目标恢复并验证配套备份，按恢复手册处理 `.restore-pending`。不得用旧二进制覆盖新 schema 充当回退；备份之后可能发生的外部发送须人工对账，UNKNOWN 不自动重发。

## 边界

Goose 按单条迁移提交，整批升级并非一个事务。这里证明的是 v23 事务内 DDL 与版本写入的回滚；之前成功提交的迁移仍然保留。未来非事务迁移或外部副作用需要独立恢复计划，不能套用本演练的回滚结论。

本阶段覆盖迁移函数取消和真实数据库会话丢失；没有声称完成操作系统 SIGKILL、主机断电、PostgreSQL 崩溃、磁盘损坏或每一个历史版本组合的验收。持久占用的异常退出保护与配套备份恢复已有独立测试，真实基础设施故障仍需部署环境演练。

## 验收

新增 `TestUpgradeInterruptedMigrationAndExplicitRecovery`，三种故障均在独立数据库执行；每次验证 DDL/版本回滚、启动门槛、占用状态及显式恢复。三种故障的定向 race 测试通过（2.704 秒）。OrbStack 重启后重新执行完整 `make ci`：格式、静态检查、构建与全部 race 测试通过，集成测试用时 229.016 秒；暂存差异检查与秘密扫描通过。本阶段只增加测试与操作文档，不改生产迁移逻辑。

下一段进入 9C 的协调生命周期，先明确各类数据的保留关系与只读预检，保护 UNKNOWN、有效幂等键、反馈证据和配额窗口。
