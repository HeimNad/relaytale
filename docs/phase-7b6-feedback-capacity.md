# Phase 7B.6 · 反馈证据总容量保护

## 问题与行为

7B.2 的限额仅适用于每个 IMAP 来源。手工导入与多个来源的合计证据仍可能持续增长。本阶段通过迁移 00011 在 `feedback_reports` 的 INSERT 后执行数据库计费，使所有正常数据库写入路径共享总额度，包括旧版本应用的导入。

固定上限为 **100,000 条证据、1 GiB 逻辑内容**，任一条件不足即拒绝新增。逻辑字节为 `octet_length(raw) + octet_length(parsed::text)`，包括原文及 PostgreSQL 规范 JSON 文本；不是数据库磁盘占用。索引、元数据、审计、WAL、TOAST 与临时空间仍需独立容量规划。现有每个 IMAP 来源 100 MiB/10,000 条限制继续有效。此限制不覆盖来源、异常回执、告警等所有辅助表，也不代替生产生命周期管理。

- 计数与证据插入处于同一事务，单行条件更新串行化并发额度竞争。
- 完全相同的 source/external_id/sha256 触发 ON CONFLICT DO NOTHING，不消耗新额度；满额仍可返回已有重复证据。
- 同一来源事件的不同内容属于新的冲突证据，正常计费。
- 审计失败导致整笔事务回滚，不留下证据或容量消耗。
- IMAP 容量失败同时回滚该封邮件的本地来源计数、回执及 UID 更新；此前已提交的邮件保持不变。已有每来源上限仍可能在全局重复检查前阻止收集。
- 没有自动删除、清理或修改历史反馈，没有把关闭反馈当作释放空间。

## 升级与运行

迁移会锁定反馈表写入，回填已有记录数量和逻辑字节，然后安装触发器；应为较大历史库安排维护窗口。历史证据即使已超过上限也保留，迁移不会为降低用量删除内容；后续新增将暂停。读取、查询、重复导入仍可进行。

额度不足被映射为 `feedback.ErrCapacity`，CLI 返回错误。IMAP 操作者应停止重复采集并核查数据库容量和待处理证据。不要手工清零计数或禁用触发器来继续运行；扩容和协调保留方案属于 Phase 9 的独立设计。不存在可通过 API 调高额度或删除证据的入口。具有数据库 DDL 权限的管理员依然可以绕过触发器；这不是抵御数据库管理员的安全边界。

新增认证后的只读 `GET /admin/v1/feedback-capacity`，所有管理角色可查询：

```json
{"records":0,"stored_bytes":0,"max_records":100000,"max_bytes":1073741824,"at_limit":false}
```

`at_limit=false` 只说明当前尚未达到硬上限，不保证剩余额度能容纳下一封邮件。数字不包含来源或地址等个人信息。端点拒绝查询参数，沿用 no-store、身份校验、并发和超时限制。数据库记录与审计故障不会被隐藏成零用量。

回退迁移仍显式拒绝，避免移除保护或丢掉计费历史。旧应用在新 schema 上仍受触发器约束，但可能只显示数据库错误而非新版本的可识别容量错误。

## 验收范围

- 隔离 schema 中制造剩余一条额度，8 个并发导入仅 1 个成功，其余返回容量不足。
- 满额重放同一证据不再次计费或写审计。
- 原文与解析 JSON 同时计费，恰好达到字节上限成功，再新增被拒绝。
- 审计失败后容量与证据回滚，恢复审计后同一内容可正常重试。
- IMAP 全局满额时游标、回执和每来源计数回滚；合成夹具恢复额度后从同一 UID 继续。
- 模拟 100,001 条历史证据超过新上限，迁移回填与实际计费一致；保留历史记录、拒绝新增且允许已有重复证据。
- 容量 API 的只读身份、未授权访问及非法参数验证。

测试只操作隔离 PostgreSQL 和合成证据，不访问真实邮箱或发送外部邮件。自动反馈处置仍未启用。
