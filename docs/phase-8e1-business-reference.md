# Phase 8E.1：业务关联 ID、标签与网站范围检索

网站提交原始 EML 时，可以额外提供业务关联 ID 和分类标签。它们保存在数据库中，跟随状态查询、接收审计及选择新版格式的 Webhook，不注入 MIME。第一版范围是 HTTP API 身份；不引入项目管理、SMTP 头解析、消息流优先级或任意 metadata。

## 提交

现有 `POST /v1/messages`、服务端 Bearer token、`message/rfc822` 请求体和 Idempotency-Key 保持。新增可选 HTTP 头：

```http
X-RelayTale-Client-Reference: order:123-notification
X-RelayTale-Tag: order_receipt
X-RelayTale-Tag: transactional
```

| 字段 | 边界 |
| --- | --- |
| client_reference | 最多一个头，1–128 个 ASCII 字符；首字符为字母/数字，其余仅允许字母、数字、点、下划线、冒号、连字符；大小写敏感 |
| tags | 最多 8 个重复 X-RelayTale-Tag 头；每个 1–32 字符，仅小写字母、数字、下划线、连字符，首字符为字母/数字；重复标签拒绝 |

可只提供关联 ID 或标签，也可均不提供。标签视为集合，按 ASCII 顺序规范化；不接受逗号拼接、空值、任意 JSON、中文或自由文本。边界错误返回 400 `invalid_business_reference`，在读正文、创建归档之前拒绝。身份始终来自认证令牌，不允许请求自选归属项目。

使用不含敏感内容的不透明 ID。不要放验证码、重置 token、邮箱、姓名或完整用户资料。字符限制无法判断某个字符串是否为秘密，调用方负责选择安全标识；这些字段会出现在有权限的网站查询、审计和新版回调里，查询 URL 也可能被调用方或反代记录。本阶段不把它们加入日志或指标标签。

业务 ID **不是幂等键，也不是授权凭据**。同一订单的多次合法通知可以共享业务 ID，必须各自使用不同的幂等键；相同业务 ID 不会自动合并或去重邮件。

## 幂等、原文与审计

无关联字段时继续使用原始 version=1 请求指纹，保证旧提交在升级后仍可用原请求/原幂等键重放。存在字段时使用 version=2 指纹，覆盖原始 EML 哈希/大小、顺序敏感的信封，以及规范化后的业务字段。

- 同一幂等键 + 同样正文/信封/业务字段：返回原 message_id，不增加归档或投递。
- 仅标签顺序不同：视为同一请求。
- 改动/删除业务 ID、增删标签或改正文/信封：返回 409，不能静默更新已有邮件。
- 并发不同请求争用同一键：数据库账本只接受一个；HTTP 在途锁可能先返回 503，之后重试仍会判为冲突。

字段与 message/recipients/events 在同一入队事务保存。MESSAGE_RECEIVED 的追加式审计包含规范化业务字段。数据库约束限制长度、集合内容和 API 来源；触发器禁止修改关联字段，以及已有业务关联消息的身份归属。历史空关联也不提供事后补写入口，避免与请求指纹及已发通知不一致。

邮件归档与出站 MIME 均保持原样，Sender/Provider/UNKNOWN 决策逻辑不变。标签不决定路由、额度或发送优先级。

## 单封状态的显式版本选择

```http
GET /v1/messages/{message_id}?schema_version=2
Authorization: Bearer <现有令牌>
```

不传参数或传 `schema_version=1` 时，保持 8D.1 响应，不增加 business。选择 2 时返回 `schema_version: 2`，在原状态响应上增加：

```json
"business": {
  "client_reference": "order:123-notification",
  "tags": ["order_receipt", "transactional"]
}
```

旧邮件在新版中显示空引用和空标签数组，不猜测关联。现有事件 `limit` / `before` 仍可使用；未知版本与重复参数返回 400。SMTP_ACCEPTED 仍非入箱证明，DELIVERY_UNKNOWN 仍禁止自动重新提交。

## 范围检索

```http
GET /v1/messages?client_reference=order:123-notification&tag=order_receipt&limit=50
Authorization: Bearer <现有令牌>
```

至少提供 `client_reference` 或 `tag`，同时提供时为 AND。第一版为精确匹配，不支持模糊/全文/前缀查询、任意字段过滤或无条件列出全部邮件。每个参数只能一次；查询字符串最多 1024 字节。`limit` 默认 50、范围 1–100。

响应为新列表契约，`schema_version: 2`，包含 `snapshot_at`、`messages`、`has_more`，有更多记录时附 `next_before`。每项仅含 message_id、当前 status/固定 description、created_at 和 business；收件人及尝试细节通过单封接口获取。空结果为 `messages: []`。

按 `(created_at, message_id)` 倒序排列；下一页保留原筛选条件并加 `before=<next_before>`。游标必须指向当前身份且符合筛选条件的 API 消息，其他网站、不存在或不匹配的游标统一返回 400 `invalid_cursor`，不泄漏对象存在性。只能检索自己身份的消息；不同网站可以使用相同业务 ID。

分页是历史浏览，不是持久变更订阅。每页独立只读快照，延迟提交的邮件可能出现在已翻过的位置；不要把游标当增量水位。撤销、轮换、来源限制、10 秒请求预算及 no-store 规则与 8D.1 相同；列表和单封查询共享读取限额，不消耗独立的发信令牌桶。

数据库新增身份/关联 ID/时间索引、身份/时间索引和标签 GIN 索引；查询仍有超时及结果上限。本阶段不声称完成大规模历史检索压测。

## Webhook 版本兼容

在 `WEBHOOK_ENDPOINTS` 中为目标显式增加 `"schema_version": 2` 并重启。省略版本保持 1；旧配置哈希保持兼容。新字段对签名算法、目标隔离、投递重试与人工重放没有影响。

版本 2 的**未来通知**带上与单封查询相同的 business 对象。已有 outbox 正文不重写，版本 1 的积压和人工重放仍为版本 1。因此网站升级时要同时接受版本 1 和 2；版本 1 通知可用 message_id 查询新版详情。切换配置不回补历史事件，不重新发送邮件。

通知正文仍由同一事件事务固定，业务字段不可变；收尾确认丢失后重试保持同一 event_id 和精确正文。字段上限保持通知小于既有 4 KiB 限制。NOT_EXPOSED 仍表示可信异步退信尚未提供。

## 升级与恢复

迁移 00015 增加受约束的业务列、索引、不可变保护和 endpoint schema_version，并替换事件捕获函数；不修改历史请求指纹或历史通知。建索引和约束检查可能持锁，应先完成停写备份并安排升级窗口。旧二进制不要与新版本并行运行；Down 要求明确降级计划，不自动删除关联与审计历史。

9A 备份包含业务列和通知版本；恢复检验额外检查新版通知的业务字段是否与消息一致。恢复回放测试验证原幂等键与业务参数仍返回原消息，以及通知正文和业务关联保持一致。

## 本地验收

- 冻结旧版指纹编码和 endpoint 配置编码，检查无字段请求/旧配置兼容。
- 字段长度、字符、重复参数、标签规范化、未知响应版本、请求体与查询边界。
- 原始 MIME 逐字节不变、重放不新增归档、业务字段变化冲突、并发不同关联只有一个请求入队。
- 相同业务 ID 多消息、跨网站隔离、相同时间分页、组合筛选、空结果、游标隐藏和凭证撤销。
- UNKNOWN 保持及关联字段不可修改；新旧 Webhook 格式并存，积压正文不变。
- 完整备份/恢复中的业务字段与通知正文一致性。

执行格式检查、go vet、构建、全套 race 单元/数据库集成测试，仅使用隔离 PostgreSQL、Fake SMTP 和本机 HTTP；未启用真实外部回调或发信。
