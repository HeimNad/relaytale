# Phase 9C.2：协调原文清理与数据库栅栏

现有 `cleanup` 和可选维护调度现在使用同一协调 EML 策略；未增加新的删除入口。默认仍预览，自动维护仍需显式开启。元数据、events、attempts、配额、反馈和审计不删除，debug 字段清理仍使用原有独立期限策略，本阶段不将其宣称为完整证据生命周期。

## 新意图与保留依赖

AVAILABLE 原文只有超过完成时间保留期、消息终态且无投递占用、进行中 attempt 或未完成/UNKNOWN 收件人，才检查下一层：永久幂等 ledger/旧 idempotency_key、PENDING/IN_FLIGHT/DEAD Webhook，以及全库未人工关闭的反馈。任一依赖存在，原文不进入新删除候选。

只读 `preflight-retention` 继续解释原因；`cleanup --eml-days ...` 提供执行前预览；`--apply` 使用以下事务流程重新核对，不接受保存的报告作为许可。API 幂等记录目前永久保留，因此对应原文可能永久被保护；DEAD 通知仍可重放，不视为自动失效。

## 并发与提交边界

1. 清理事务先取得反馈互斥锁，再锁住目标 message（FOR UPDATE）。反馈 INSERT 的数据库触发器使用同一事务级 advisory lock。
2. 等待锁之后，以新的 READ COMMITTED 语句重新检查依赖和期限。幂等、通知、活跃收件人/attempt 的触发器持有 message 的 KEY SHARE，直到依赖事务提交；清理必须等其结束后重新观察。
3. 将 PURGE_PENDING 与维护审计同事务提交，使用同步提交。数据库触发器再次检查依赖，阻止直接跳过应用层检查。
4. 意图确认提交之后才删除受目录约束的文件、同步目录，再提交 PURGED、事件和维护审计。任一不确定提交仍走既有保守错误与可恢复协议。

先提交的反馈或消息依赖会阻止新意图。先提交的删除意图则拒绝随后新增的幂等引用、非归档通知依赖及投递重激活；不会隐式把退休原文恢复为 AVAILABLE。旧 API 入队先写 ledger 再写 message 的原子流程仍支持：缺失的 message 在当时不被当作退休；延期外键和 message 主键约束防止复用已有 ID。

ARCHIVE_PURGED 事件通知仅依赖保留的元数据，允许在退休后创建或重放，避免删除完成事件卡死自身事务；其他通知不能在退休后进入 PENDING/IN_FLIGHT/DEAD。终态收件人与完成 attempt 的正常维护不需要重新启用原文。

## 已提交意图与后到反馈

PURGE_PENDING 是已经提交的删除决定，并不是新候选。文件可能已经删除、完成提交可能尚未确认；新反馈无法恢复它。因此后到反馈仍完整保存，但不撤销既有意图。恢复路径仍检查终态、占用与未完成投递，不重新应用新候选的全局反馈/引用过滤。

这一边界也适用于升级前留下的 PURGE_PENDING；升级不会悄悄撤销旧意图或假装原文仍存在。升级前应先盘点待完成意图及关联历史，必要时保持停写人工核对。不得通过重置 AVAILABLE、删除反馈或 ledger 来释放容量。

## 升级

迁移 00024 增加数据库触发器与函数，不重写历史数据，也不改变旧 PURGED 记录。按 [升级手册](phase-9b6-upgrade-drills.md) 停写迁移、重新应用权限再启动；Down 拒绝自动降级。依赖写入与新退休意图要求 READ COMMITTED；只读 REPEATABLE READ 预检不受影响。

触发器以调用者权限执行，没有 SECURITY DEFINER 或新增权限提升。数据库 owner、超级用户、禁用触发器、手写文件删除仍可绕过机制，不属于支持的运行接口。支持的清理代码按反馈锁→message 排序；直接 SQL 或旧二进制的不同锁顺序可能被数据库判为死锁并回滚，不能据此重试文件删除。新二进制的 schema 门槛拒绝不完整迁移。

保留依赖增多意味着同样期限下候选会减少，这是升级行为变化。批量与默认开关保持原样，容量紧张时先核对反馈与通知，不能绕过保护。数据库与文件的原子性仍靠意图/完成协议，不承诺跨两者单事务或端到端 exactly-once。

## 验收

定向测试覆盖：实际清理与失败恢复、反馈先提交阻断新意图、意图先提交后反馈不破坏恢复；退休后幂等、通知及投递重激活拒绝；反馈、ledger、通知状态、收件人状态和 attempt 状态写入未提交时，用 pg_stat_activity 的真实锁等待建立屏障，提交后验证清理重新读取并保留原文；数据库直接意图也不能跳过依赖。

旧备份与沙箱 PURGED 状态测试用仅限合成数据库管理员的事务局部触发器绕过，模拟迁移前历史；正常运行权限无此能力。常规清理测试改用独立数据库，避免其他测试导入的真实隔离反馈污染全局保留条件。

最终触发器强化版本的定向 race 测试通过（10.483 秒），完整 `make ci` 通过格式、静态检查、构建与全部 race 测试，集成测试用时 245.930 秒；暂存差异检查与离线秘密扫描通过。全部使用隔离 PostgreSQL + Fake SMTP，不清理真实存档。直接意图并发回归验证了触发器显式 FOR UPDATE 升级，避免普通 UPDATE 的 NO KEY UPDATE 与引用 KEY SHARE 兼容而漏掉新引用。
