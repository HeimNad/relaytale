# Phase 8B · 受控 HTTP 发信入口

新增默认关闭的 `POST /v1/messages`，适用于受信任的服务端客户端；通过 HTTPS 或受控本机连接使用。它复用 8A 幂等入队和既有 worker；仍需 Phase 8C 的真实 HTTP 故障与取消验收，当前不作为生产发布完成标志。

## 配置与凭证

环境变量 `SEND_API_KEYS` 为 JSON 数组，空值关闭整个 `/v1/` 入口。每项为：

```json
[{"id":"<稳定的 UUID>","token":"rts_<32 字节随机数的小写十六进制>","allowed_from":["sender@example.test"]}]
```

此示例是占位符。使用密码生成器生成 32 字节随机值，并用 UUID 生成器生成身份 ID。最多 32 个身份，每个白名单最多 32 个精确邮箱地址；不是域名通配规则。配置只通过受保护环境传递，不提交到 Git。配置校验拒绝未知/重复字段、重复身份/令牌及与管理 API 或 metrics 重用的令牌。

启动事务将令牌摘要同步到 api_keys，并追加 API_SEND_CONFIGURED 审计（身份 ID、发件白名单，不含令牌）。SMTP 密码和管理令牌不作为发信凭证。若身份 ID 已被其他类型的 API key 使用，启动失败。

轮换时保留 ID、替换 token 并重启；幂等范围保留，旧令牌不再通过。删除配置中的身份后重启即撤销；数据库历史行保留，不代表仍有有效访问权限。配置是有效身份集合的来源。每个请求还重新检查数据库 enabled 与令牌摘要；已开始处理的请求不会因之后的配置/数据库变动被追溯撤回。重新显式配置同一 ID 会在启动时启用它。修改白名单也需重启。

## 请求格式

- 方法/路径：`POST /v1/messages`，不接受查询参数。
- `Authorization: Bearer <独立发信令牌>`，只允许一个头。
- `Content-Type: message/rfc822`，不接受参数、压缩内容或 JSON/Base64 包装。
- `Idempotency-Key`：1–128 字节可打印 ASCII，不含空格，只允许一个头。
- `X-RelayTale-From`：一个裸邮箱地址。
- `X-RelayTale-To`：每个收件人单独一行，可重复头名，1–100 个不同地址，不使用逗号拼接。
- 正文：完整 RFC822/MIME 原文，使用 CRLF 行结束且以 CRLF 结束。中文、附件等按 MIME 规则预先编码；不自动生成或重写 MIME/Message-ID。

信封 From 与 MIME From/Sender 都必须符合当前身份白名单。信封地址只规范域名大小写，local-part 保留大小写。规范后的重复收件人被拒绝。带 Origin 或 cross-site Fetch 标记的浏览器请求被拒绝，不开放 CORS。

示例（自行设置变量；仅对预定测试目标执行）：

```sh
curl --request POST "$RELAYTALE_URL/v1/messages" \
  --header "Authorization: Bearer $RELAYTALE_SEND_TOKEN" \
  --header 'Content-Type: message/rfc822' \
  --header 'Idempotency-Key: application-request-unique-id' \
  --header 'X-RelayTale-From: sender@example.test' \
  --header 'X-RelayTale-To: recipient@example.test' \
  --data-binary @message.eml
```

响应 `202`：

```json
{"message_id":"<Gateway UUID>","replayed":false,"status":"GATEWAY_ACCEPTED"}
```

同键同请求重放也返回 202，原 ID 不变，replayed 为 true。这只证明网关已保存入队事实，不代表远端接受或入箱；消息可能随后被抑制或暂停。即使原消息已接受、被抑制或处于 UNKNOWN，重放也不会创建新任务。

| 状态 | 含义 |
| --- | --- |
| 400 | 信封、幂等键、原文/行结束等不合法 |
| 401 | 凭证缺失、无效或已撤销 |
| 403 | 发件地址不允许或浏览器来源拒绝 |
| 404 | 入口未配置或路径不存在 |
| 405 / 415 | 方法 / 内容类型不支持 |
| 409 | 同一幂等键对应不同请求内容 |
| 413 | 正文大小超过上限 |
| 429 | 全局/每身份并发或速率限额，带 Retry-After |
| 503 | 在处理相同键、资源不足、存储/数据库失败等；用相同请求与相同键重试 |

连接中断、超时或 503 都不能通过更换键来重试。客户端不能从失败响应推断一定没有提交；8A 的持久化记录用于后续去重。

## 资源与文件边界

固定全局 4 个活跃请求，每身份最多 2 个；每身份令牌桶每秒补充 1 次、突发 10 次。重放和已认证的非法请求也消耗速率预算。限额在进程内，重启重置，依赖现有单实例约束，不是集群配额或公网抗 DDoS 保证。

正文使用 MAX_MESSAGE_BYTES，HTTP 启用时最多 100 MiB；默认仍为 25 MiB。配置需提供至少两份最大正文大小的 spool 预算，每请求预留两份以覆盖快照和存档临时文件，并与出站 worker 共用资源预算。请求操作及正文读取期限为 10 秒，外层 HTTP 服务仍有自己的超时；大邮件/慢链路必须在 Phase 8C 实测后评估。

正文先流式写入受限的私有临时快照，打开后立即 unlink，正常返回及进程退出都会释放文件。校验完整原文、权限和指纹后，才在每身份/幂等键的数据库锁内查询旧记录；已知重放不发布额外 EML。同时竞争同键的 HTTP 请求可能返回 503，再次重试即可查询已提交结果。

新请求仍经原有 LocalStore 原子发布并同步落盘，再同步提交队列。数据库结果不明确时保留已发布原文；本阶段不自动删除这类候选孤儿文件。不同内部写入路径若绕过 HTTP 每键锁，仍可能产生多份候选存档，8A 的数据库唯一约束继续保证只入队一次。完整孤儿回收、响应丢失与取消场景属于 8C，不能把临时快照回收等同于这些问题已全部解决。

## 验收

配置校验、独立身份、发件权限、格式拒绝、已知长度与未知长度超大正文、重放/冲突、并发文件数量、限速、默认关闭、数据库撤销和启动时轮换均有测试；另有本机 TLS 请求穿过实际路由、多个收件人正确入队的测试。存档失败测试确认无消息/幂等记录，临时文件和资源预留释放；Fake SMTP 验证原 MIME 与既有 worker 行为。

本阶段不配置真实发信令牌、不连接真实邮箱、不发送外部测试邮件。
