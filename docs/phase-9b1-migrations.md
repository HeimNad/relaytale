# Phase 9B.1：显式迁移与只读启动检查

本阶段解除“服务启动必须拥有 schema 修改权限”的耦合，增加 PostgreSQL 迁移互斥，并拒绝不兼容 schema。它不完成全部 9B：单实例及运行/维护互斥、最小权限部署与密钥轮换分别继续验收。

## 行为变化

正常服务启动不再自动执行 Goose Up。绑定 HTTP/SMTP、同步身份/回调或启动 worker 之前，使用只读 repeatable-read 事务检查 goose_db_version 的完整已应用版本集合。空数据库不创建版本表；版本空洞、回退记录或未知版本会拒绝启动。只比较最新版本号不足以发现空洞，因此按历史顺序还原每个版本状态再核对所有内嵌迁移。此检查验证迁移历史，不是全量 schema 指纹或 SQL 文件校验和；手工删表、篡改历史等仍需权限边界和维护流程防止。

`relaytale migrate --offline` 显式执行内嵌迁移，成功后再次验证 schema，输出通用 JSON 结果。命令只读取 DATABASE_URL，不要求 TLS、发送密钥或 HTTP 配置；拒绝缺少 --offline 或多余参数。五分钟总期限，支持终止信号；不输出原始数据库错误或连接凭证，不提供自动 Down。

迁移入口先使用 PostgreSQL SessionLocker（数据库级 ID 734219509）保护 pending 检查及版本表初始化，再由 Goose 原生同执行连接的 SessionLocker（ID 734219510）保护实际迁移。两个锁按固定顺序取得。入口额外占用一个连接，迁移连接池需至少两个连接；应用默认上限为十。同进程调用先做可取消串行准入，避免多个等锁连接耗尽连接池；跨进程互斥仍由 PostgreSQL 强制。并发迁移串行，等待受上下文限制，数据库会话断开释放锁。启动检查取同 ID 的共享事务锁，若已有迁移持锁则立即拒绝检查；它不在运行期间持有锁。

这是显式升级互斥，不是运行实例 fencing。`--offline` 仍是操作者确认，不能阻止谎报停写、旧版本程序或手工 SQL。运行过程中发起迁移仍不安全；9B.2 才继续补运行/维护互斥。当前必须停掉所有写入者和发送者。

## 首次部署

1. 准备数据库及开发 TLS，按 README 配置。
2. `docker compose run --build --rm relaytale migrate --offline`。
3. `docker compose up --build -d`，验证 ready 和配置。

## 已有部署升级

1. 停止 Gateway、反馈采集和外部维护进程；确认所有发送均已停止。
2. 使用 9A 的停写备份流程保存数据库及 EML。不要删除卷。
3. 构建目标版本，用同一目标版本执行 `docker compose run --build --rm relaytale migrate --offline`。
4. 成功后启动一个实例，验证 ready、队列、凭证与保守状态。迁移失败保持停写，检查历史；不要盲目改版本表。

重跑同一迁移命令是无待执行迁移时的幂等操作。历史 Down 中有显式禁止回退的迁移；升级失败不自动降级。较旧二进制遇到新版本历史拒绝启动；回退应使用明确恢复方案并对账备份之后的外部发送。

后续将为迁移与运行配置分开的数据库角色；本阶段没有宣称运行角色已无 DDL 权限。现有 Compose 仍是开发配置。

## 验收

隔离 schema 测试覆盖空库检查零创建、已迁移库通过、数据库 read-only 下检查通过、未知版本与历史空洞拒绝、持锁时检查拒绝、等待迁移取消零写入、并发初始化无重复及结束后锁释放。CLI 测试确认停写参数先于数据库访问检查。首次故障注入发现 Goose Up 的 pending 检查会在内部拿锁前初始化版本表，因此补上入口锁，再验证阻塞取消不会创建版本表。

完整 make ci 通过（格式、go vet、go build、全部 go test -race；隔离 PostgreSQL 集成测试 202.135 秒）。最终同进程准入/连接池保护后重跑格式、相关 go vet 与迁移 race 专项通过（1.683 秒）。实际二进制验证空库拒绝启动且零 schema 写入、显式迁移、两个独立进程并发初始化、重复迁移、ready 与正常退出；单实例、故障升级恢复、最小权限、密钥轮换及生产发布尚未通过本阶段验收。
