# Phase 8E.2a · 网站提交预算

2026-10-02 完成本地验收。8E.2 的第一个独立检查点：网站提交预算。共享 Provider 账号预算、消息流及公平调度、邮件有效期仍待后续实现；本阶段不改变 SMTP worker 的投递或重试语义。

## 配置与计费单位

在 `SEND_API_KEYS` 的各身份中增加可选 `budget`：

```json
[{"id":"<稳定 UUID>","token":"rts_<32 字节随机值的小写十六进制>","allowed_from":["sender@example.test"],"budget":{"minute":20,"hour":200,"day":2000}}]
```

这是占位示例。三个值均为 0..2147483647 的整数；省略或 0 表示不限制对应窗口。它们分别是滚动 1 分钟、1 小时、24 小时内**新接收的信封收件人数**，所有已启用的窗口都必须满足；按数据库预留时刻计入窗口，不是自然日，也不是令牌桶的突发额度。一封邮件发给三个不同地址扣 3，整个提交一起接受或拒绝，不自动拆分。

配置由管理员控制，启动时同步到数据库并记录不含令牌的审计。保留身份 UUID 时，换令牌、重启、修改或暂时关闭预算都保留用量。新建身份代表新的网站额度，不能用更换 UUID 代替密钥轮换。迁移会回填过去 24 小时现有 API 幂等记录的收件人数；历史不因新启用预算而自动豁免。

本预算约束 HTTP 网站身份。SMTP 账号不受本预算约束；需要 SMTP 网站预算时必须另行接入，不能声称已覆盖。原有每个身份的请求速率/并发限制继续独立生效。

## 请求与错误

HTTP 发信请求不新增预算参数，原文和幂等指纹保持不变。

| 响应 | 业务含义 | 网站处理 |
| --- | --- | --- |
| 202 | 新请求已提交，或原请求幂等重放 | 保存原 message_id；不代表已投递/入箱 |
| 429 `recipient_budget_exhausted` | 当前滚动窗口没有足够额度 | 保留同一请求与幂等键稍后重试；`Retry-After: 60` 是重查建议，不保证 60 秒后有额度 |
| 422 `recipient_batch_exceeds_budget` | 本次收件人数本身超过至少一个窗口的总上限 | 调整管理员预算或业务批次；原样等待不会解决 |
| 409 `idempotency_conflict` | 同键对应不同请求 | 修正业务调用；不会扣额度 |

同键同请求即使额度已满、预算被降低或原邮件处于 UNKNOWN，仍返回原结果，不再次扣额或投递。查询状态和 Webhook 不消耗网站提交预算。成功接受后，即使全部被 suppression 阻断、最终失败或 UNKNOWN，也不退还额度；它计量网关接受的工作，而非成功送达。原 Provider 预算仍按每次投递尝试的收件人数独立计量，重试/切换不再次收取网站提交额度。

## 事务与故障边界

- 数据库保存分钟/小时/天上限；各进程在同一身份行上取得 `FOR NO KEY UPDATE` 锁后，以新的 READ COMMITTED 查询快照核对用量。该锁与幂等账本外键的 KEY SHARE 锁兼容，避免并发锁升级死锁。
- 新提交的幂等账本、预算预留、消息/收件人、事件和 Webhook 捕获在同一事务中提交。预算不足不创建正式 EML，也不留下幂等占位。
- HTTP 请求仍需读入有界、open-unlink 的临时快照才能校验原文和指纹。预算检查发生在快照验证之后、正式 EML 发布之前。数据库身份锁跨越有界文件发布，受请求超时限制；不适合拿它宣称无限吞吐。
- 文件保存失败、事务回滚或确定的提交失败不会扣额。发布 EML 后提交结果不确定时保留原文，网站用原键重试；不冒险删除可能已被数据库引用的文件。
- 每次新接收都记录预算，包括没有设置上限的身份。预留历史只追加；数据库通过复合外键约束预算的消息/网站必须属于同一幂等记录。尚未提供这份账本的自动清理，历史增长需纳入运维规划。
- 备份恢复保留预算配置、使用量与幂等记录，并校验预算的身份及收件人数一致性。过去 24 小时的幂等记录缺少预算行时阻止验收。

这不是 Provider 的实际账单或发送额度。多个网站仍可能竞争同一个 Provider，本阶段也没有实现跨网站公平调度。所有服务进程必须使用一致的管理员配置；启动会重新同步预算，不提供多实例配置协调。生产单实例/迁移互斥和密钥轮换仍属于 9B 阻断项。
